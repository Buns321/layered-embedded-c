# Idea 2：基于 `.ioc` 只读解析的可视化/命令行框架配置工具

> **状态**：构想记录（待立项实施）
> **核心前提**：在 Coding Agent 辅助下工具初期开发成本可忽略，且本框架确定面向多个后续嵌入式工程复用。

## 1. 背景与构想演进

### 1.1 被否决的初始路径：生成 `.ioc` + 调用 CubeMX CLI

最初构想由自定义 CLI 根据硬件描述文件生成 `.ioc`，再调用 STM32CubeMX 命令行（`-q <script>`）生成底层工程并自动配置驱动。该路径经评估后被**明确否决**，原因如下：

1. **等价于逆向维护 ST 私有芯片数据库**：`.ioc` 为 Java Properties 格式的未公开私有配置，生成合法 `.ioc` 需同时满足引脚复用功能（AF）、DMA Stream/Channel 互斥、PLL 时钟树合法性与 FreeRTOS NVIC 优先级分组，跨芯片或 CubeMX 升级极易静默产出非法配置。
2. **无法实现真正的一键闭环**：CubeMX 生成代码仍无法满足本工程的全部静态分配与中断约束（例如 `Core/Inc/FreeRTOSConfig.h` 必须在 `USER CODE Defines` 强制覆写 `configSUPPORT_DYNAMIC_ALLOCATION=0`，`USART2` 需手动补齐 `USART2_IRQn` 与中断处理函数），生成后仍需脆弱的正则补丁脚本二次修改 `Core/`。

### 1.2 反转后的核心定位

将数据流反转为：**CubeMX 管硬件（只读真源） → 工具解析 `.ioc` → JSON 管 Framework 装配 → 单向生成板级代码与构建清单**（同构参考：RT-Thread Env/`menuconfig`、ESP-IDF `menuconfig`）。

## 2. 目标工作流与产物

1. **硬件配置阶段（STM32CubeMX GUI）**：
   - 用户按标准流程在 CubeMX 中完成芯片选型、时钟树、外设参数、DMA/中断与引脚分配，生成 `.ioc` 与 `Core/`、`Drivers/` 代码。
2. **资源扫描阶段（`.ioc` 只读解析）**：
   - 工具只读解析 `.ioc` 中的表层稳定键值（如 `Mcu.CPN`、`Mcu.IP*`、`<Pin>.Signal`、`<Pin>.GPIO_Label`），提取当前工程实际启用的可用外设句柄与 GPIO 引脚池。
3. **模块选配与绑定阶段（可视化前端 / JSON）**：
   - 用户在工具中勾选需要启用的框架模块（如 `RTT_Log`、`WHT101`、`MPU6050`、`TB6612` 等），并在结构化表单或 `board_fw.json` 中将其绑定到 `.ioc` 提供的真实资源与参数（周期、限幅、PID 等）。
4. **校验与代码生成阶段（CLI 后端）**：
   - 命令行后端执行资源存在性、引脚/外设互斥冲突与参数边界校验；校验通过后，单向生成只读的板级装配源码、头文件与 CMake 模块启用清单（以及可选的硬件映射 Markdown 文档）。

## 3. 价值分析与长期风险

### 3.1 成立的工程价值

1. **编译前拦截硬件绑定错误**：在生成阶段即可捕获句柄不存在、同一外设或 GPIO 被多个模块重复占用、PWM `Period` 与驱动 `max_duty` 不匹配等配置失误。
2. **消除“按需编译裁剪”与“严格报错”之间的矛盾**：仅将勾选的模块编入 CMake 构建（零 Flash/RAM 浪费），且生成代码只初始化已勾选模块，彻底消除运行期 `if (huart != NULL)` 静默跳过逻辑，漏配即直接报错。
3. **降低多工程复用时的 API 记忆成本**：新开工程时无需逐个查阅各 `*_cfg_t` 结构体字段、物理单位与初始化顺序，由工具引导输出合规的静态实例与初始化链路。
4. **硬件映射文档自动同步**：直接依据 `.ioc` 与 `board_fw.json` 导出引脚与外设占用表，消除手写维护 `doc/hardware-map.md` 的同步漂移。

### 3.2 长期使用隐患（与开发成本无关）

1. **框架源码与工具 Schema 漂移**：若工具硬编码模块列表与配置结构体字段，每次新增驱动或调整 `*_cfg_t` 都会导致工具与框架源码脱节。
2. **高频调参效率倒退**：引脚绑定属于低频操作，而 PID 增益、速度上限、死区属于高频调试参数；若每次调参都必须打开可视化界面重新生成，效率会低于直接修改文本配置。
3. **生成代码与手写代码混编冲突**：若允许在生成产物内手写代码（类似 `USER CODE BEGIN/END`），二次生成将带来合并冲突与解析破坏。
4. **跨 STM32 系列 `.ioc` 键名差异**：F4/G4/H7 底层外设参数键名存在差异，过度解析底层寄存器配置会降低跨芯片复用稳定性。

## 4. 工具形态对比

| 维度 | 形态 A：JSON 真源 + 可选 TUI/Web 前端 + CMake 自动生成（推荐） | 形态 B：独立重型桌面/Web GUI，必须通过界面操作生成 | 形态 C：纯 Kconfig（`menuconfig`）生成宏 + 手写 `board_cfg.c` |
| :--- | :--- | :--- | :--- |
| **`.ioc` 资源校验与防冲突** | **强**（解析 `.ioc` 做存在性与互斥检查） | **强** | **无**（Kconfig 不感知 `.ioc` 引脚与外设） |
| **高频调参效率** | **高**（可直接编辑 JSON，构建时自动触发重新生成） | **低**（每次调参需切换窗口点击保存与生成） | **中**（文本编辑 `.config` 略晦涩） |
| **Git Diff 与代码审查友好度** | **高**（结构化 JSON 差异清晰，生成文件明确标记只读） | **中**（复杂配置格式 Diff 噪音大） | **高** |
| **多项目与 CI 自动化集成** | **极高**（CLI `validate/gen` 可接入 `tools/check.py` 与 CI） | **低**（强依赖人工 GUI 操作） | **高** |

## 5. 硬性设计边界（落地准入条件）

后续正式实现该工具时，须遵守以下 4 条架构边界：

1. **单一真源与单向全量覆写**：
   - `.ioc`（硬件真源） + `board_fw.json`（框架配置真源） → 单向全量覆写生成 `board_gen.c` / `board_gen.h` / `board_gen.cmake`。
   - 生成文件顶部标注 `DO NOT EDIT`，**严禁**设置 `USER CODE` 手写槽位；自定义业务逻辑置于独立的 `User/` 文件中调用生成接口。
2. **模块元数据下沉至各模块目录（防 Schema 漂移）**：
   - 工具本体保持为通用引擎，不硬编码 `WHT101`、`MPU6050`、`RTT_Log` 等具体模块。
   - 每个可复用模块在自身目录维护轻量描述文件（如 `module.schema.json`，声明所需 `.ioc` 资源类型、配置字段、物理单位、合法范围与 CMake 源码/目标），工具运行时动态扫描加载。
3. **`.ioc` 解析器严格克制深度**：
   - 仅提取跨 STM32 系列最稳定的表层资源：`Mcu.CPN`、已启用外设实例（`USART*`/`I2C*`/`SPI*`/`CAN*`/`TIM*`）、以及引脚 `.Signal` 与 `.GPIO_Label`；外设底层时序、波特率与 DMA 参数继续完全交由 CubeMX 管理。
4. **可视化前端与无界面 CLI 后端彻底解耦**：
   - 后端提供无交互纯 CLI（如 `python3 tools/fwcfg.py validate` / `gen`），直接接入 CMake 构建前置步骤与 `tools/check.py` 门禁。
   - 可视化前端（终端 TUI 或本地单页 Web UI）仅作为 `board_fw.json` 的交互式编辑器，不直接承载校验或代码生成核心逻辑。
